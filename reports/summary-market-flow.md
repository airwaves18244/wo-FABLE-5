# Market Flow / Market Terminal — Architecture Review
(Sonnet subagent summary)

## 1. Purpose & domain
"Market Terminal" (repo: Market-flow) is a **read-only analytics desktop application** (Windows-targeted) for observing market turnover and money flow on the Moscow Exchange via the **Finam Trade API**. It answers "where is money going, which sectors lead, how does capital flow between stocks/futures/bonds." Explicitly v1 is analytics-only — it does **not place orders** (order-routing exists only as a stubbed/simulated capability for a later "trading workstation" mode). All UI copy and most documentation are in Russian; code identifiers are in English. The product vision expands over its roadmap from a market-overview terminal into a fuller "workstation" with backtesting, footprint/delta analysis, paper trading, MOEX ALGOPACK integration, and an options module.

## 2. Architecture
**Stack**: Rust workspace (edition 2021, rust-version 1.80) + Tauri 2 desktop shell + Svelte 5/TypeScript/Vite frontend.
- `crates/finam-proto` — gRPC stubs for Finam Trade API, generated via `tonic-build` + vendored `protoc` from sanitized `.proto` copies (feature-gated `grpc`).
- `crates/domain` — pure analytics core (turnover, money flow/MFI/CVD, market breadth, sector rollups, sector rotation RRG, cross-asset flow matrices, alerting, plus V2: backtesting engine, delta/footprint detectors, paper-trading simulator, and Phase 10-12 additions for options pricing/vol-smile/strategy builder). Deliberately has **zero dependency on gRPC/Tauri/DuckDB**, so it builds/tests cross-platform in CI.
- `crates/data` — Finam adapter: auth/JWT refresh, rate limiting (per-method sliding window, ~200 req/min), exponential backoff w/ jitter, secret storage (`SecretStore` trait; in-memory + OS-keyring implementations), live streaming with auto-reconnect (~24h), offline replay source.
- `crates/storage` — DuckDB-backed storage behind a `Store` trait, with `MemStore` (in-memory, cross-platform testable) and `DuckStore` (native DuckDB, feature-gated); schema migrations, ingest of bars/snapshots/instruments/sector classification, batch-poll scheduler + history backfill.
- `crates/app` — Tauri orchestration: `AppState`, IPC command/DTO layer (26 commands kept in sync across Rust registration and TS client), tracing/telemetry init, async ingest scheduler, live-mode wiring, replay support.
- `frontend/` — Vite + Svelte 5 + TS; ECharts (treemap/heatmap/Sankey/scatter/gauge/pie/line) + TradingView Lightweight Charts (candles); typed IPC client with a **mock mode** letting the whole UI run in-browser without a Rust backend; 37 components across dockable panels for stocks/sectors, futures, bonds, an aggregate "sum of all" view, live Time&Sales/DOM panels, and alerts; localStorage-based settings.

**Layering rule** (explicitly documented): all analytics math lives in `domain`, agnostic to network/UI/DB; `data`/`storage`/`app` are thin adapters. Enforced via feature-gating (`grpc`, `duckdb`, `tauri`, `keyring`, `ingest`, `live-trading` all optional), keeping default/CI build light while heavy native deps (webkit2gtk, bundled DuckDB C++, tonic/prost) stay opt-in. Approx. size: ~17,000 lines Rust, ~6,300 lines frontend TS/Svelte.

## 4. Key design decisions & patterns
- **Trait-based ports/adapters**: `MarketData`, `Store`, `SecretStore`, `Strategy`, `OrderRouter` are traits with a pure/testable in-memory implementation plus a feature-gated "real" implementation (gRPC, DuckDB, OS keyring, `SimBroker`/`FinamOrderRouter`) — nearly the entire system is testable without network/native deps.
- **Feature-flag-gated heavy dependencies** to keep default CI build fast/cross-platform.
- **Mock-mode frontend**: TS IPC client can run entirely against mocks (`mock.ts`), so UI dev/testing needs no Rust backend — mock, real IPC client, and Tauri command registration are manually kept in sync at 26 commands.
- **Secret resolution priority chain**: env var → `.env` file (custom dependency-free parser, tested) → OS keyring — documented as excluding `.env` from the repo via `.gitignore` (contradicted in practice — see risks).
- **Phased, spec-first delivery**: every phase has a written spec before/alongside implementation, with a separate design brief cross-referencing roadmap task IDs — heavy planning-document-driven development.

## 5. Quality/risk observations
- **Critical: a live-looking secret is committed to git.** `.env` (containing a `Finam_API_SECRET=tapi_sk_...` value) is tracked in git (confirmed via `git ls-files`), added in the Phase-12 merge commit, despite `.gitignore` explicitly listing `.env` and both README/SUMMARY stating the secret "does not enter the repo." Direct contradiction between documented intent and actual repo contents — a genuine secret-hygiene failure regardless of whether the key is still live.
- Phases 10–12 are only partially done (domain-only); network/storage/frontend layers for MOEX ALGOPACK, history backfill, and options UI are still pending, mixing "done" (0-9) and "in-progress" (10-12) phases in one roadmap on `main`.
- No end-to-end/packaging CI (MSI/NSIS untested in automation — the actual installable artifact is never verified by CI).
- Live-data path (real gRPC auth, OS keyring round-trip) is only unit/contract-tested; true integration tests are `#[ignore]`d or need manual/network setup, leaving the riskiest integration point unverified by CI.
- Frontend test coverage is thin relative to Rust (16 vitest tests / 4 test files vs. 244+ Rust tests across 52 files) — most correctness guarantees sit in `domain`; frontend is comparatively unverified.
- Heavy reliance on generated/vendored proto and bundled native deps (DuckDB, protoc) increases build complexity/time.
