# Playbook: Architecture & Planning for Agent-Driven Development

**Generic recommendations and templates.** Distilled from recurring patterns in plan-first, multi-model, AI-agent-operated development — deliberately not tied to any specific project. Each section states the failure mode it prevents, the rule, and a copy-paste template where useful.

---

## Part I — Planning discipline

### 1. Continuation-first planning (anti cold-start)

**Failure mode prevented:** every new idea spawns a fresh repo/PRD/architecture doc; the same product gets re-designed from zero multiple times; ontologies and module maps diverge because sessions have no memory of prior work.

**Rules:**
- Every planning session **starts by reading a portfolio index** and must classify its work as *continuation* of an existing lineage or *genuinely new* (new requires one written sentence of justification).
- A restart of an existing product is a **decision, never a default**. It requires a written restart-vs-continue memo (template §8) weighing working code against clean-slate appeal. "The old docs are messy" is not a restart reason; "the core abstraction is wrong and untestable" might be.
- New architecture documents for an existing system must be written as **delta documents** ("what changes vs. the implemented baseline"), never as from-zero specs. A from-zero spec of an existing system silently forks the truth.

**Template — `PORTFOLIO.md`** (lives in one well-known repo; one line per active repo):

```markdown
# Portfolio Index
| Repo | Lineage | Purpose (1 line) | Status | Canonical branch | Supersedes / superseded-by |
|------|---------|------------------|--------|------------------|----------------------------|
| ...  | product-A | ... | active / paused / archived | main | ... |

## Session gate (mandatory first step of any planning session)
1. Which lineage does this work continue? ______
2. If "none": one sentence why no existing lineage fits: ______
3. Which existing artifacts (docs, schemas, code) does this work consume or extend? ______
```

### 2. Cap planning work-in-progress

**Failure mode prevented:** a growing shelf of polished, unfilled templates and 70-task TODO lists with zero started tasks — planning output outpacing execution indefinitely.

**Rules:**
- **A plan is not "done" until its first gate has fired.** A methodology/pipeline/template that has never processed one real work item is untested code; run one real item through it as its acceptance test before writing the next methodology.
- Enforce a WIP limit: **no new planning artifact for a lineage while an approved plan for that lineage has zero completed tasks.** The correct next step is executing task 1, not refining the plan.
- Size plans to the execution horizon you can actually see. Prefer a fully-specified **phase of 5–15 tasks + a coarse backlog** over 70 uniformly-detailed tasks; detail decays — tasks specified months before execution will be re-planned anyway, so the up-front detail is waste.

### 3. Claims in planning docs must be verifiable

**Failure mode prevented:** a PRD asserting "previous version already works end-to-end" that no one can verify from the repo; status lines contradicting reality; roadmaps quoting test counts nobody re-checks.

**Rules:**
- Every factual claim in a PRD/roadmap ("X works", "Y is tested", "prototype achieves Z") carries a **pointer to evidence**: a repo+commit, a CI run, a benchmark file. Unverifiable claims are marked `[UNVERIFIED]` and cannot justify scope decisions.
- Status sections in long-lived docs are **build artifacts, not prose**: either generated by CI or checked by a script that diffs claimed numbers (test counts, phase checkmarks) against measured reality, failing CI on drift. In an agent-operated repo, self-reported completion is the primary integrity threat — agents write optimistic status prose, and it fossilizes.
- Separate the three document species and never mix them in one file: **spec** (what should be true), **status** (what is true, machine-checked), **decision log** (why — append-only ADRs).

### 4. Decompose NFRs before planning against them

**Failure mode prevented:** one scary compound NFR ("50k events/s to pixels in 100ms") distorting an entire plan, when it actually conflates independent budgets that different layers own.

**Method — for every NFR:**
1. Ask: *which layers does the data traverse, and what does each layer actually need to sustain?* Split the NFR into **per-layer budgets** (ingest rate ≠ storage flush rate ≠ IPC payload rate ≠ paint rate). A boundary that aggregates/bins/samples decouples the budgets on either side of it.
2. Classify each sub-budget: **trivially met / needs a benchmark / needs a design / unknown-risky**.
3. Anything "unknown-risky" gets a **time-boxed spike before epic commitment**, with numeric pass criteria and a named fallback:

```markdown
## Spike S-<n>: <risky bet>
Time box: ≤ N days. Runs BEFORE tasks: <epic ids>.
Hypothesis: <specific, falsifiable, numeric>
Bench setup: <deterministic, seeded, target hardware stated>
PASS: <numbers>          KILL: <numbers>
Fallback if KILL: <pre-decided plan B — decided now, while calm>
Verdict recorded in: docs/decisions/ADR-<n>.md
```

### 5. Shared ontology before parallel artifacts

**Failure mode prevented:** two teams/sessions independently invent taxonomies/schemas for the same domain (e.g., a research corpus and its consumer app), producing hundreds of artifacts that can't interoperate and require painful reconciliation later.

**Rules:**
- The moment two artifacts will both refer to the same domain concepts, **freeze a tiny shared schema first** — even 15 lines of YAML spec is enough. Retrofitting a schema onto 40+ hand-written docs costs 10× writing it first.
- Keep axes orthogonal: don't mix *category* with *venue/platform/context* in one enum (the classic smell: one "category" that is actually a location). Categories on one axis, tags for everything orthogonal.
- Make prose artifacts machine-consumable from day one via **structured frontmatter** with a committed JSON-Schema validator in CI:

```yaml
---
id: <stable-slug>            # never reused
class: <one of the closed enum>
tags: [<orthogonal facets: venue, platform, ...>]
status: <draft | active | deprecated | dead>
lifecycle: <stage in your promotion pipeline>
params: {name: {min: , max: , default: }}
evidence: [<claim-ids / links>]
---
```
- Deliberately include **known-dead/negative examples** in any corpus that feeds an automated promotion pipeline — they are regression tests: a pipeline that promotes a known-dead item is broken.

## Part II — Architecture

### 6. Pure core + thin adapters (keep doing this — but enforce it mechanically)

The single most successful pattern observed: a **dependency-free domain core** (no network/UI/DB/vendor SDK imports; SI units; pure, deterministic, idempotent functions) surrounded by thin adapters (`data`, `storage`, `app`, `ui`), each adapter pairing a trait/interface with an in-memory test double and a feature-gated real implementation. Benefits compound in agent workflows: cheap models can safely work inside the core because it builds and tests anywhere, including sandboxes without licensed/native dependencies.

**The gap to close:** the rule is usually enforced by convention in a doc. **Enforce it in the build** — a CI check (import-linter, cargo-deny/custom lint, ArchUnit, dependency-cruiser…) that fails when the core imports an adapter-layer namespace. Agents follow docs *usually*; builds fail *always*.

Companion rules:
- **Units and encoding conversions live only at the boundary** (one conversion module), never scattered.
- **One error type** crossing each boundary, defined once on the owning side.
- Side effects batched into **one transaction per user-visible command** (one undo step, natural idempotency checkpoint).

### 7. Never hand-synchronize a boundary — generate it

**Failure mode prevented:** the same interface (IPC commands, API surface, DTOs) maintained by hand in 2–4 places (server registration, typed client, mocks, docs), drifting apart as it grows.

**Rules:**
- Every cross-language/cross-process boundary has **exactly one source of truth**, and everything else is generated from it (Rust→TS via specta/ts-rs, OpenAPI→clients, protobuf→stubs). Decide the codegen *direction* once, explicitly — usually: the implementation-owning side generates for consumers.
- Mocks implement the **generated** interface so drift is a compile error, not a runtime surprise.
- Add a **contract test** in CI: enumerate the surface from both sides, diff, fail on mismatch. This catches the "registered but not generated" hole codegen alone misses.

### 8. Restart-vs-continue and other one-way decisions: write the memo

**Failure mode prevented:** months of execution against an undocumented restart decision (or non-decision); one-way calls made implicitly by whichever session happened to run that day.

**Template — decision memo / lightweight ADR** (append-only, `docs/decisions/ADR-NNN-<slug>.md`):

```markdown
# ADR-NNN: <decision>
Date / Status: proposed | accepted | superseded-by ADR-MMM
## Context (what forced the decision; link evidence, not vibes)
## Options (2–4, each: cost, risk, what it forecloses)
## Decision (one sentence, imperative)
## Rationale (why this beats the runner-up, explicitly)
## Reopen trigger (the specific external evidence that would justify revisiting)
## Execution handoff (who/what tier executes; first 3 tasks)
```

The **reopen trigger** line is what stops future agent sessions from cold-relitigating settled calls: they either present the named evidence or execute the decision.

For restart-vs-continue specifically, require the memo to state: LOC and test count of the existing system; which of the new spec's ideas the existing system *already implements*; and the measured (not vibed) defect that makes continuing untenable. Default verdict is **continue + delta doc**; restart must be argued.

### 9. Secrets in agent-operated repos: remove the class of error

**Failure mode prevented:** a real credential committed to a public repo *despite* `.gitignore` listing it and docs promising it never happens — because agent workflows bulk-stage files (`git add -A`) and force-add paths, and a convention only has to fail once.

**Rules, in order of importance:**
1. **No file-based secrets at all** in repos that agents operate. Resolution chain: environment variable → OS keyring/secret manager. Delete `.env` support from the code, not just from the repo — as long as the code path exists, the file will exist, and one bulk-stage will commit it.
2. Defense in depth anyway: platform push protection + secret scanning ON for every repo; `gitleaks` (or similar) pre-commit hook in the standard repo template; CI job that fails on detection.
3. If a leak happens: **rotate first, purge second** (`git filter-repo` across *all* refs — leaked secrets survive on unmerged branches), and assume the value was harvested the moment it hit a public remote.

### 10. Portable playbooks must be stack-parameterized

**Failure mode prevented:** an in-house architecture playbook that hard-codes framework choices (e.g., mandates React) while the flagship product uses something else — so the playbook is either ignored or forces pointless rewrites, and both lose authority.

**Rule:** split guidance into the **load-bearing 80%** that survives any framework (monorepo layout; framework-free `packages/core`; enforced dependency direction core←ui←apps; perf budgets as CI blockers; IPC rules; one error model) and **per-stack appendices** for the parts that are genuinely framework-specific. Over-specifying the replaceable layer is how playbooks die. Perf budgets belong in the portable core, as *numbers enforced by CI* (bundle size, LCP/INP, cold start, memory, IPC p95) with "budget breach = blocker-severity review finding".

## Part III — Operating a multi-model agent workforce

### 11. Tiered routing: pay for reasoning, not volume — but add portfolio memory

The tier ladder (frontier model for architecture/critique → mid-tier for bounded implementation → small model for mechanical work) with escalate-on-two-failures is sound. Its observed blind spot: **per-task cost optimization with no cross-task memory** — nothing in the ladder ever asks "did we already build/decide this?". Fixes: the continuation gate (§1) and ADR log (§8) are *part of the routing system*, not documentation extras: the orchestrator reads them before dispatching.

**Template — routing table (one per project, in the plan doc):**

```markdown
| Task class | Tier | Effort | Verification substitute (see §12) |
|---|---|---|---|
| One-way architecture calls, ontology design, restart decisions | top | high/max | decision memo + adversarial 2nd pass |
| Numerical/financial/safety-critical correctness | top→mid | high | golden vectors + property tests (§12) |
| Cross-layer features, perf work, security review | upper-mid | med/high | dual independent review |
| Contract-driven implementation, tests, refactors | mid | med | tests + reviewer verdict block |
| Mocks, docs, citations, boilerplate, mechanical edits | small | low | schema/lint checks |
Escalation: 2 failures at a tier → one tier up, with a written ≤20-line summary (never a raw transcript).
De-escalation: allowed when a task proves mechanical.
```

### 12. Convert judgment into protocol (the succession principle)

**Failure mode prevented:** dependence on any single top-tier model (or single senior human) as the un-substitutable verifier — which breaks the day that capability becomes unavailable.

**Method:** for each class of work currently requiring top-tier judgment, ask *what mechanical protocol lets a weaker judge reach the same verdict?*
- **Numerical correctness:** generate **golden test vectors once** from independent references (established libraries, hand-computed edge cases), commit them, and add **property-based invariants** (parity relations, monotonicity, conservation laws). Thereafter any tier verifies against oracles instead of re-deriving math.
- **Risk-critical review:** replace one deep review with **two independent passes with different briefs** (implementation review vs. adversarial "how does this lose money/leak data" red-team) plus a literal CI-gated checklist for the known kill-criteria. Independence substitutes for depth.
- **Architecture:** the decision-memo format (§8) *is* the protocol — a structured brief with options/evidence/recommendation lets a mid-tier model contribute usefully and a stronger occasional reviewer audit cheaply. The dangerous prompt is the unframed "figure out the architecture".
- Keep the **residue visible**: decisions that genuinely don't decompose go in a named queue (batch them for whenever top-tier reasoning is available) rather than being silently absorbed by a weaker tier.

### 13. Session hygiene: main-is-truth

**Failure mode prevented:** real content stranded on auto-named session branches while `main` is empty; a portfolio where cloning any default branch finds nothing; work discoverable only through one person's memory.

**Rules:**
- **A session ends with merge-or-PR the same day.** An agent session's branch is a transaction, not a home.
- Weekly triage: session branches older than N days are merged or deleted — never left as the sole copy of anything.
- `main` is the default branch, is never empty, and is what every doc links to. If content must live long on a branch, `main` at minimum carries a README pointing at it.
- One repo = one product. Incubating project B inside project A's repo "temporarily" always outlives the intention; the cost (polluted history, mixed toolchains at root, divergent stale copies after the split) exceeds the 30 seconds of creating a repo. Empty placeholder repos are also debt — create the repo when the first artifact exists.

### 14. TODO/task schema: every task self-verifying

**Failure mode prevented:** long task lists where "done" is a checkbox someone (or some agent) ticks, with no way to audit; tasks with no tier/effort routing, forcing re-triage at dispatch time.

**Template — task entry:**

```markdown
### T-<phase>.<n>: <imperative title>
Tier: <top|mid|small>  Effort: <low|med|high>  Depends: [T-x.y]
Scope: <1–3 sentences; what is IN and what is explicitly OUT>
Contract: <the interface/schema/doc this implements — link, don't restate>
DoD (machine-checkable, all must hold):
- [ ] `<exact command>` exits 0        # tests/lint/build
- [ ] <artifact> exists at <path>      # e.g. generated client, ADR
- [ ] <contract test / budget check> passes
Verify-by: <command or CI job name — how a *different* session proves it later>
```

The `Verify-by` line is the important one: it makes every "done" claim re-checkable by a session with zero context, which is the normal audience in agent workflows.

### 15. The one-page pre-flight (pin it)

Before any significant planning or architecture session:

```markdown
□ Read PORTFOLIO.md — continuation or new? (new ⇒ 1-sentence justification)
□ Read the lineage's ADR log — which decisions are settled? (reopen only with named trigger evidence)
□ Does a working implementation of any part already exist? ⇒ delta doc, not from-zero spec
□ Any compound NFR? ⇒ split per-layer; risky sub-budgets get spikes with numeric PASS/KILL
□ Two artifacts sharing concepts? ⇒ freeze the shared schema first
□ Any new boundary? ⇒ pick the codegen source of truth now
□ Secrets touched? ⇒ env/keyring only; no file path exists in code
□ Plan size ≤ execution horizon (5–15 fully-specified tasks; rest is coarse backlog)
□ Every claim has evidence or [UNVERIFIED]; every task has Verify-by
□ Session will end with merge-or-PR to main
```
